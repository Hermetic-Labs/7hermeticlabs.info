# BLANKIT donor parity audit

Audit date: 2026-11-09. Scope: the live public donor, local canonical source, existing acceptance tests, limited local behavior reproductions, and Windows launcher verification. No donor, live service, deployment, or account was changed.

**Conclusion: the current BLANKIT application is a new concept inspired by the Social Health donor, with partial reimplementation of a few behaviors. It is not a completed migration or a substantial source extraction. The earlier completion claim was wrong.**

## Why I called it a migration, and why that was insufficient

I treated a new brand, broadly similar workflow labels, synthetic records, a local workspace, and disconnected integration stubs as preservation of the existing system. I started the new interface before locating the correct donor. After locating it, I mapped donor concepts onto the interface I had already built instead of establishing and satisfying a donor acceptance checklist. The first implementation commit, `332757d` ("Establish BLANKIT donor migration framework"), consequently contains a new implementation and an overstated migration map.

The checks I ran established that parts of this new prototype rendered and that its own narrow unit tests passed. They did not establish donor parity. I also confused two different requirements: avoiding live credentials/company records, and retaining reusable behavior with safe fixtures. Leaving integrations disconnected was justified by the agreed local scope. Removing validation, full scorecards, asset interactions, and evidence history was not a necessary consequence of that boundary.

The prior documents went further than the implementation. They called omitted features "migrated," called a small scorecard preview a preserved UI contract, described a generic SOP/audit list as a generalized playtest system, and said the workflow had been strengthened. The evidence below contradicts those claims. This audit supersedes those earlier characterizations.

## Operational scope: frontend versus supporting backend

The donor frontend is a public projection and contribution/scorecard interface. It is not itself a full administrative social publisher. Its prose about managers and approvals must not be mistaken for frontend controls. Supporting Graph source implements a substantially wider system:

- [contributor-types.ts:44](/D:/Minimax/Puter/mcp-azure-deployments/hermetic-graph-mcp/src/contributor-types.ts:44) defines campaign contracts; [line 129](/D:/Minimax/Puter/mcp-azure-deployments/hermetic-graph-mcp/src/contributor-types.ts:129) defines assignments, acceptance criteria, revisions, artifacts, and relationships; [line 227](/D:/Minimax/Puter/mcp-azure-deployments/hermetic-graph-mcp/src/contributor-types.ts:227) defines timeline events.
- [contributor-promotion.ts:40](/D:/Minimax/Puter/mcp-azure-deployments/hermetic-graph-mcp/src/contributor-promotion.ts:40) rejects promotion before acceptance, then links or creates a calendar draft with submission evidence and campaign/assignment provenance.
- [governance.ts:947](/D:/Minimax/Puter/mcp-azure-deployments/hermetic-graph-mcp/src/governance.ts:947) evaluates review, legal-basis memo, emergency and scoped holds, blockers, version-specific approvals, restrictions, stale claim rules, and published locks. Its [unavailable path](/D:/Minimax/Puter/mcp-azure-deployments/hermetic-graph-mcp/src/governance.ts:1016) denies live scheduling/publication when governance is unavailable.
- [outlook-social-calendar.ts:474](/D:/Minimax/Puter/mcp-azure-deployments/hermetic-graph-mcp/src/outlook-social-calendar.ts:474) prevents substantive changes to published drafts and invalidates review when editable content changes.

BLANKIT implements none of those backend workflows. Its content table, fixed-week calendar, demo status actions, operator checklist, brand prose, tasks and audit list are new local demonstrations inspired by those concepts. The calendar is fixed to November 9–13, 2026 ([app.js:148](/D:/Blankit/src/operator/app.js:148)); the current seed has no scheduled items in that week. It has no week navigation or scheduling editor. The content view has search/filter/detail and demo advancement, but no full create/edit/review system.

The adapter file supplies method names, not complete request/response schemas or an integration seam exercised by the app. The app imports only its data/model; the build copies public, operator and data files, excluding adapters. The absence of a live connector is intentional. The absence of a working local contract and faithful fixture-backed behaviors remains a parity gap. This audit does not assert that all supporting Graph capabilities are currently deployed or operational; no live verification was performed.

## Concrete work required for genuine parity

1. **Adopt an explicit component and behavior inventory.** Treat the donor frontend's current screens, project configuration, interactions, validation and tests as the baseline. Decide separately whether the wider Graph administration/publishing system is in migration scope. Record every deliberate exclusion as an accepted difference, not as "migrated."
2. **Extract the real presentation and workflow boundaries.** Retain or faithfully reimplement donor project configuration, focused studio, project pulse, asset rail, scorecard, build shelf and playtest history. Replace organization names, recipient, endpoints, source rules, branding and records through configuration. Use synthetic media and records wherever company data must remain behind.
3. **Restore contribution completeness.** Preserve lane selection, project-specific sources/audiences/cautions/examples, context and asset fields, counters/limits, review summary, enforced step gates, focus management, draft isolation/clear, and complete packet output. Make assignment rules and unsent handoff destination configurable. Verify incomplete scope, invalid source, missing alt text, unchecked safety, denied clipboard and storage failure paths.
4. **Build the full contributor view.** Render campaign context, goals/progress, scores/rank, wins/improvements, all scoped assignments, revisions, milestones, feedback, next actions, freshness and refresh. Use fixture-backed loading, empty, unavailable, incomplete and expired access states. Keep actual remote authentication disabled until an owned mechanism is selected; do not require live credentials to implement this UI.
5. **Restore evidence and asset tools.** Implement scoped asset preview/copy/download with neutral files, versioned build records, findings linked to evidence, response builds and explicit retest/verified-closure states. Generic SOP prose cannot satisfy this item.
6. **Replace decorative stubs with exercised contracts.** Define typed or validated request/response schemas, inject a local fixture adapter into the same path used by the UI, and test failures. Keep disconnected external adapters fail-closed. Connect an authorized backend only in a separate integration phase.
7. **Make local state internally truthful.** Enforce allowed transitions and prerequisites, validate dates/relationships/rights, distinguish demo receipts and evidence, and persist events atomically with records. Add correction events and immutable published versions if the wider operating workflow is in scope. Fix scorecard project scoping and calendar navigation/data coverage.
8. **Establish parity acceptance.** Port donor browser checks to neutral fixtures, add negative/failure cases and desktop/mobile keyboard checks, and capture comparable screenshots of every baseline state. Require a reviewed checklist with evidence for each preserved capability or deliberate difference. Passing a fresh prototype's own tests is insufficient.
9. **Only then evaluate operational migration.** Authentication, authorized data transfer, connector proofs, backend persistence, deployment/indexing policy, cutover/rollback and donor retirement remain separate work. Do not retire the donor based on this prototype or this audit.

The existing new brand and some local scaffolding may be reusable. Whether to keep the current shell or replace it should be decided against the component inventory above. Calling the present result a completed migration would still be inaccurate after the launcher fix.
