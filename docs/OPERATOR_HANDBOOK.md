# Blankit operator handbook

## First day

1. Read `SECURITY.md` and confirm whether the workspace is local or authenticated.
2. Read the project lane’s job, public boundary, next gate, voice, and channels.
3. Learn the three independent status dimensions: review, publication, and outcome.
4. Open the brand library and verify the approved language and asset rights.
5. Run one synthetic contribution through the studio without sending or publishing it.
6. Read the current decision/handoff queue and correction trail.

## Normal operating loop

1. Frame the objective, audience, owner, proof, project, and outcome definition.
2. Create or accept a contribution against a named project and assignment.
3. Capture the source, claim, channel treatment, asset reference, and alt text.
4. Review claims, consent, rights, privacy, tone, and accessibility.
5. Record approval separately from release readiness.
6. Schedule or publish only through an authorized connector and only after an explicit human decision.
7. Store the provider receipt and do not silently edit a published record.
8. Open an outcome check, attach evidence, and distinguish attention from real-world impact.
9. Append corrections with reason, owner, time, and superseded record.

## Status vocabulary

- **Planned / draft** — work exists; it is not reviewed.
- **In review** — a named human review is pending.
- **Approved** — the content passed review; this does not schedule or publish it.
- **Ready** — destination, source, asset, accessibility, and timing requirements pass.
- **Scheduled** — a confirmed queue or calendar receipt exists.
- **Published** — the provider confirms publication.
- **Pending verification** — publication happened; outcome evidence is still open.
- **Verified outcome** — the stated outcome has named evidence and reviewer acceptance.

## Corrections

Never erase history to make a record look clean. Append a correction event, identify the affected record, explain why it changed, name the owner, and preserve the prior version. Published content is treated as immutable; reuse requires a new draft.

## Handoffs

Every handoff should name the project, assignment, owner, current state, evidence, blocker, next action, recipient, and authority boundary. A handoff packet is not proof that it was sent or accepted.
